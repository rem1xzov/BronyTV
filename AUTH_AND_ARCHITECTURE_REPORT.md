# BronyTV: архитектура, email-авторизация и защита ИИ-чатов

Дата анализа: 12 августа 2026.

## 1. Что находится в репозитории

Активный production-стек запускается корневым `docker-compose.yml`:

1. **`Brony_Video-main/`** — React 18 SPA (Create React App), интерфейс видео, форума, новостей, профиля, поддержки, админки и ИИ-чатов.
2. **`BronyTV/BronyTV/`** — ASP.NET Core 9 API, EF Core 9, PostgreSQL, видео, пользователи, комментарии, форум, новости, поддержка и администрирование.
3. **`AiBronyTV/AiBronyTV/`** — ASP.NET Core 9 + Semantic Kernel, SSE-стриминг ответов DeepSeek, история диалогов и дневные лимиты.
4. **Nginx** во frontend-контейнере — раздаёт SPA и видео, `/api/*` проксирует в основной API или AI-сервис.
5. **PostgreSQL 16** — основная схема `public`; AI-история и лимиты теперь хранятся отдельно в схеме `ai`.

Каталог `BronyTV-main/` — устаревшая дублирующая копия проекта. Корневой compose её не использует. Её не следует разворачивать как production-версию.

## 2. Реализованный поток email-авторизации

### Регистрация

`POST /api/auth/register`

- валидирует email, пароль, расу и username;
- создаёт **неподтверждённую** запись пользователя в PostgreSQL;
- генерирует криптографически случайный шестизначный код;
- хранит только BCrypt-хеш кода;
- отправляет код через SMTP;
- возвращает HTTP `202 Accepted` и **не создаёт сессию**.

Код действует 15 минут. Незавершённые регистрации удаляются через 24 часа.

### Подтверждение

`POST /api/auth/confirm-email`

- принимает email и шестизначный код;
- ограничивает число ошибочных вводов пятью попытками;
- после успеха помечает email подтверждённым, удаляет хеш кода и создаёт HttpOnly JWT-cookie `bronytv_session`;
- повторный вызов для уже подтверждённого аккаунта не создаёт сессию. Это закрывает обнаруженную возможность passwordless-входа через endpoint подтверждения.

### Повторная отправка

`POST /api/auth/resend-email-confirmation`

- новый код можно запросить не чаще одного раза в 60 секунд;
- endpoint не раскрывает существование подтверждённого аккаунта;
- состояние регистрации хранится в БД и не теряется при перезапуске контейнера.

### Вход

`POST /api/auth/signin`

- требует email и пароль;
- неподтверждённый пользователь получает `409 Conflict` и переводится на экран кода;
- JWT выдаётся только подтверждённому аккаунту и содержит подписанный claim `email_verified=true`.

## 3. Обязательная авторизация для ИИ-ботов

Защита сделана на двух уровнях.

### Сервер

AI-сервис проверяет тот же JWT, который выпускает основной API. Для:

- `GET /api/bots`;
- `POST /api/chat/stream`;

обязательны:

- валидная подпись JWT;
- правильные issuer/audience и срок действия;
- роль `User`;
- claim `email_verified=true`.

Без cookie возвращается `401`, с неподтверждённым токеном — `403`. Поэтому обойти ограничение прямым HTTP-запросом к `/api/chat/stream` нельзя.

Username и роль больше не принимаются от браузера: AI-сервис берёт их только из подписанного JWT. Это закрывает подмену роли `Admin`/`Owner` в JSON-запросе.

Пользовательский `sessionId` из браузера получает namespace с ID авторизованного пользователя. Дневной лимит привязан к ID аккаунта, поэтому очистка `localStorage` его не сбрасывает. На endpoint действует rate limit 12 запросов в минуту на пользователя.

### Клиент

Страница `/bots` показывает экран входа/регистрации, пока нет подтверждённой сессии. После `401/403` клиент обновляет состояние сессии и предлагает войти повторно. SSE-запрос использует HttpOnly cookie и больше не отправляет доверенные данные о роли.

## 4. SMTP

Production-конфигурация переведена на Gmail SMTP:

- host: `smtp.gmail.com`;
- port: `587`;
- режим: явный STARTTLS через MailKit;
- sender/user задаются переменными `EMAIL_SMTP_USER` и `EMAIL_FROM_ADDRESS`.

App password намеренно **не записан в Git**. Его нужно поместить в `EMAIL_SMTP_PASSWORD` файла `.env` или в secret-хранилище среды развёртывания. IMAP используется только в E2E-тесте для получения кода и приложению не требуется.

Полный Gmail SMTP + IMAP E2E успешно пройден: письмо принято Gmail, код извлечён из входящего письма и подтверждён через API.

## 5. Дополнительное усиление безопасности

- Добавлены IP rate limits для входа, регистрации, подтверждения и повторной отправки.
- Удалено автоматическое создание аккаунтов `admin/admin` и `rainbowdash/rainbowdash`.
- Legacy-admin создаётся только при явно заданных `ADMIN_BOOTSTRAP_LOGIN` и пароле от 12 символов.
- Владелец/администратор больше не определяется по публичному username. Роли можно безопасно назначить подтверждённым email через `OWNER_EMAIL` и `ADMIN_EMAIL`.
- Удалены закоммиченные production-подобные JWT/DB defaults из активной конфигурации.
- Compose требует явно задать `POSTGRES_PASSWORD`, `JWT_KEY`, `EMAIL_SMTP_PASSWORD` и `DEEPSEEK_API_KEY`.
- Основной API отклоняет старый JWT, если пользователь удалён или его email не подтверждён.
- Валидация AI-запросов ограничивает session ID, персонажа и сообщение (до 2000 символов).
- После достижения дневного лимита AI больше не делает платный LLM-запрос.
- История AI и дневные лимиты перенесены из памяти процесса в PostgreSQL-схему `ai`.

## 6. Развёртывание

```bash
cp env.example .env
```

Заполнить как минимум:

```dotenv
POSTGRES_PASSWORD=<длинный случайный пароль>
JWT_KEY=<результат openssl rand -base64 48>
EMAIL_SMTP_PASSWORD=<выданный SMTP-пароль>
DEEPSEEK_API_KEY=<ключ DeepSeek>
OWNER_EMAIL=<email владельца, если нужен Owner>
FRONTEND_ORIGIN=https://bronytv.ru
```

Затем:

```bash
docker compose up -d --build
```

При запуске основной API применит EF-миграцию `20260812120000_AddEmailConfirmationSecurity`. AI-сервис идемпотентно создаст схему `ai` и свои таблицы.

После обновления пользователям со старой cookie без claim `email_verified` потребуется один раз войти заново для доступа к AI.

## 8. Отдельные технические долги

1. `BronyTV-main/` — legacy-дубликат с устаревшей конфигурацией; лучше удалить отдельным изменением после подтверждения, что он никому не нужен.
2. Create React App / `react-scripts` устарел. `npm audit` показывает 46 транзитивных уязвимостей (в основном toolchain; 11 low, 12 moderate, 21 high, 2 critical). Рекомендуется отдельная миграция frontend на Vite и актуальный build stack, а не `npm audit fix --force`.
3. В исходном проекте нет постоянных unit/integration test-проектов; выполненные проверки были запускными. Для CI желательно добавить xUnit + API integration tests и frontend component tests.

## 9. Полный Docker E2E

После установки Docker Engine 26.1.5 и Docker Compose 2.26.1 выполнена полная сборка и запуск корневого `docker-compose.yml` с новой пустой PostgreSQL volume.

Во время проверки обнаружены и исправлены дополнительные проблемы исходного проекта:

- исторические миграции `AddUsername` и `ExpandUsernameAndAvatarEmoji` выполнялись раньше создания таблицы `Users` и ломали запуск на чистой БД;

Итоговые проверки на чистой БД:

- все четыре контейнера запускаются;
- 13 обнаруживаемых EF-миграций применяются;
- создаются 9 сезонов, таблица новостей, форумные колонки и две AI-таблицы;
- frontend, seasons, news и forum отвечают `200`;
- анонимный доступ к AI отвечает `401`;
- полный email E2E один раз успешно прошёл: регистрация `202`, получение кода через IMAP, подтверждение `200`, `/auth/me` `200`, `/api/bots` `200`, подтверждённый профиль Owner;
- авторизованные CRUD-проверки форума, новостей, поддержки и административного списка прошли успешно.

### SMTP-блокер устранён

Первоначальный SMTP-провайдер исчерпал баланс и возвращал `Failed to send mail No balance`. После перехода на Gmail SMTP выполнен повторный тест на новой чистой БД:

- регистрация — `202`;
- письмо получено в Gmail через IMAP;
- код подтверждения найден;
- подтверждение — `200`;
- `/auth/me` — `200`;
- защищённый `/api/bots` — `200`;
